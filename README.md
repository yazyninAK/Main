# Мониторинг объявлений (mali oglasi)

Автоматическая проверка новых объявлений на https://2bike.rs/cikloberza/mali-oglasi,
фильтрация по критериям и уведомления в Telegram и по email (через GitHub Issues,
см. ниже). Работает бесплатно и автономно через GitHub Actions (cron), без сервера
и без API сайта.

## Как это работает

1. `.github/workflows/monitor.yml` запускает `scripts/main.py` два раза в день
   (07:00 и 19:00 UTC = 09:00 и 21:00 по Белграду). Расписание меняется в
   поле `cron` этого файла — формат обычный cron (мин час * * *).
2. `scripts/scraper.py` скачивает страницу и парсит список объявлений.
3. Объявления сравниваются с `data/seen.json` (уже виденные) — новые проверяются
   по фильтрам из `config.yaml`.
4. При совпадении — уведомление в Telegram и создание GitHub Issue (с
   упоминанием вас) через `scripts/notify.py`; GitHub Issue приходит вам
   на почту как обычное уведомление GitHub.
5. `data/seen.json` коммитится обратно в репозиторий, чтобы состояние сохранялось
   между запусками.

## Настройка

### 1. Наборы фильтров (можно несколько)

Редактируются в [`config.yaml`](config.yaml) — **прямо на GitHub**, без
скачивания репозитория: откройте файл → значок карандаша (Edit) → внесите
правки → Commit changes. Изменения подхватятся автоматически на следующей
плановой проверке, либо запустите проверку сразу вручную: вкладка **Actions
→ Monitor mali oglasi → Run workflow**.

Блок `filters:` — это **список именованных наборов условий**. Каждое новое
объявление проверяется по **всем** наборам сразу (не только по первому
подходящему), и в уведомлении будет указано, под какой набор (или наборы,
если подошло сразу под несколько) оно попало:

```yaml
filters:
  - name: "Bosch Gen5, M/L, 700Wh+, до 1500км"
    must_include: [...]
    criteria: {...}
    exclude_any: []

  - name: "Второй набор"
    must_include: [...]
    criteria: {...}
    exclude_any: []
```

**Чтобы добавить новый набор** — скопируйте блок целиком (от `- name:` до
следующего `- name:` или до конца файла), вставьте копию под первым
набором и измените в ней название и условия. **Чтобы отключить набор** —
удалите его блок или закомментируйте каждую строку символом `#`.

Внутри каждого набора:
- `must_include` — список групп `any_of`. Объявление должно содержать хотя
  бы одно слово из **каждой** группы (группы между собой — И, слова внутри
  группы — ИЛИ). Добавить новый обязательный критерий — добавить ещё одну
  группу `any_of`. Добавить синоним к существующему — дописать строку в
  нужный `any_of`.
- `exclude_any` — стоп-слова: если встретится любое из них, объявление
  пропускается под этим набором, даже если остальное совпало. Удобно
  отсеивать "куплю/ищу", запчасти и т.п.
- `criteria` — числовые/технические критерии:
  ```yaml
  criteria:
    battery_wh_min: 700       # минимальная ёмкость батареи, Втч
    mileage_km_max: 1500      # максимальный пробег, км
    frame_sizes: ["M", "L"]   # допустимые размеры рамы
  ```
  Сайт не даёт под эти параметры отдельный фильтр, поэтому они ищутся в
  тексте объявления через простые правила (например "800Wh" → батарея,
  "predjeno 300 km" → пробег, при этом "25 km/h" не путается с пробегом).
  Это эвристика, не точный разбор: **объявление отклоняется по этому
  критерию, только если значение явно указано в тексте и не подходит под
  условие.** Если продавец просто не написал ёмкость батареи или размер
  рамы — объявление не отклоняется, чтобы не пропустить реально подходящий
  вариант из-за неполного текста. Чтобы отключить критерий — `null` (для
  чисел) или `[]` (для `frame_sizes`).

Сравнение идёт по заголовку и полному тексту страницы объявления,
без учёта регистра. Все наборы фильтров используют один и тот же источник
объявлений — категорию из `site.category_url` (см. ниже); если понадобится
мониторить ещё и другую категорию/URL отдельным набором — скажите, дорабатывается.

### Фильтры левой панели сайта (бренд, цена, «скрыть проданное» и т.п.)

Задаются простыми текстовыми полями в блоке `site:` файла `config.yaml` —
никаких URL руками собирать не нужно, скрипт сам строит ссылку с нужными
параметрами:

```yaml
site:
  category_url: "https://2bike.rs/cikloberza/mali-oglasi/bicikli-6/elektricni-bicikli-13"
  hide_sold: true          # скрыть проданные
  hide_no_price: false     # скрыть объявления без цены
  brands: []                # напр. ["Cube", "Trek"] - список брендов см. в scripts/scraper.py (BRAND_IDS)
  price_min: null           # напр. 500
  price_max: null           # напр. 2000
  price_currency: "EUR"     # EUR или RSD
```

Чтобы что-то изменить — просто меняете значения полей (true/false,
числа, список брендов) и коммитите файл на GitHub, как обычно.

`category_url` — единственное поле, которое всё ещё указывает на URL, но
оно задаёт саму категорию (не меняется через фильтры) и трогать его
обычно не нужно.

Фильтр брендов (`brands`) на сайте, судя по всему, относится к бренду
велосипеда, а не мотора — использовать его для поиска "Bosch Gen 5" не
надёжно (продавец может не проставить такой тег на бренд мотора). Для
этого признака по-прежнему используется текстовый поиск в `must_include`
ниже. Город/радиус в фильтрах сайта пока не поддержан (требует отдельного
запроса к сайту для определения id города) — скажите, если понадобится,
добавлю.

### 2. Уведомления

**Telegram** — нужны 2 секрета репозитория: **Settings → Secrets and
variables → Actions → New repository secret**

| Секрет | Значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен бота от @BotFather |
| `TELEGRAM_CHAT_ID` | Ваш chat_id (см. ниже, как получить) |

1. В Telegram: `@BotFather` → `/newbot` → получить token
2. Написать боту любое сообщение
3. Открыть `https://api.telegram.org/bot<TOKEN>/getUpdates`, найти `"chat":{"id":...}`

**Email** — отдельных секретов не нужно. Вместо SMTP-пароля скрипт
создаёт GitHub Issue в этом репозитории на каждое подходящее объявление,
с упоминанием `@<владелец репозитория>` в тексте — GitHub сам присылает
за это email на адрес, привязанный к вашему GitHub-аккаунту (обычная
системная функция уведомлений GitHub, работает "из коробки"). Всё, что
для этого нужно, у workflow уже есть автоматически (`GITHUB_TOKEN`,
права `issues: write` в `.github/workflows/monitor.yml`).

Убедитесь, что в настройках вашего GitHub-аккаунта включены email-уведомления
для упоминаний: **Settings → Notifications → убедитесь, что "Email" отмечен
для "Participating, @mentions and custom"**.

Письмо будет выглядеть как обычное уведомление GitHub про issue, а не
как отдельное красивое письмо — зато без единого пароля.

### 3. Запуск

Workflow срабатывает автоматически по расписанию. Проверить/запустить вручную:
**Actions → Monitor mali oglasi → Run workflow**.

## Ограничения GitHub Actions (бесплатный план)

- Публичные репозитории: неограниченные минуты для cron.
- Приватные репозитории: 2000 минут/месяц бесплатно.
- Scheduled workflows автоматически отключаются, если в репозитории не было
  push более 60 дней — в этом случае нужно вручную включить workflow заново
  (Actions → workflow → Enable).
- Точность cron не гарантирована день-в-день (может быть задержка в несколько минут).

## Как работает поиск по критериям

`site.category_url` в `config.yaml` указывает сразу на отфильтрованную сайтом
подкатегорию "Električni bicikli" (`.../bicikli-6/elektricni-bicikli-13`) —
это надёжнее, чем скачивать всю категорию (5944+ объявлений) и фильтровать
вручную.

Список объявлений на сайте не содержит текста описания — только заголовок,
цену и продавца. Поэтому для НОВЫХ объявлений (которых ещё нет в
`data/seen.json`) скрипт дополнительно открывает страницу самого объявления
и ищет ключевые слова из `config.yaml` (например "bosch" + "gen 5") в полном
тексте страницы. Уже виденные объявления повторно не проверяются.

Список отсортирован сайтом по дате публикации/**поднятия** (новые и
пролонгированные — сверху), поэтому скрипт подгружает страницы по 32
объявления одну за другой, пока не встретит объявление, которое уже видел
раньше (до 10 страниц за один запуск, для защиты от зависания при сбоях).

## Отсеивание поднятых/пролонгированных объявлений

Продавцы могут "поднимать" старые объявления — тогда они снова оказываются
на первой странице, хотя объявление не новое. Чтобы их не путать с
реально новыми:

- У каждого объявления есть числовой id (стабильный, не меняется при
  поднятии). Скрипт запоминает **максимальный увиденный id**
  (`max_known_id` в `data/seen.json`).
- Объявление считается по-настоящему новым, только если его id **больше**
  этого максимума. Старое поднятое объявление имеет id меньше максимума —
  оно будет пропущено, даже если раньше не встречалось скрипту.
- Первый запуск (когда `data/seen.json` ещё нет) только строит базовый
  список и запоминает текущий максимальный id — уведомления в этот раз
  не отправляются, чтобы не было лавины писем про уже существующие
  объявления.

## Статус

Селекторы проверены на реальной сохранённой странице сайта — парсер рабочий.
Требуется добавить секреты (см. выше), после чего мониторинг заработает
автоматически.
