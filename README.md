# Мониторинг объявлений (mali oglasi)

Автоматическая проверка новых объявлений на https://2bike.rs/cikloberza/mali-oglasi,
фильтрация по критериям и уведомления в Telegram и по email (через GitHub Issues,
см. ниже). Работает бесплатно и автономно через GitHub Actions (cron), без сервера
и без API сайта.

## Как это работает

1. `.github/workflows/monitor.yml` запускает `scripts/main.py` два раза в день
   (07:00 и 19:00 UTC = 09:00 и 21:00 по Белграду). Расписание меняется в
   поле `cron` этого файла — формат обычный cron (мин час * * *).
2. `scripts/scraper.py` скачивает страницу и парсит список объявлений.
3. Объявления сравниваются с `data/seen.json` (уже виденные) — новые проверяются
   по фильтрам из `config.yaml`.
4. При совпадении — уведомление в Telegram и создание GitHub Issue (с
   упоминанием вас) через `scripts/notify.py`; GitHub Issue приходит вам
   на почту как обычное уведомление GitHub.
5. `data/seen.json` коммитится обратно в репозиторий, чтобы состояние сохранялось
   между запусками.

## Настройка

### 1. Наборы фильтров (можно несколько)

Редактируются в [`config.yaml`](config.yaml) — **прямо на GitHub**, без
скачивания репозитория: откройте файл → значок карандаша (Edit) → внесите
правки → Commit changes. Изменения подхватятся автоматически на следующей
плановой проверке, либо запустите проверку сразу вручную: вкладка **Actions
→ Monitor mali oglasi → Run workflow**.

Блок `filters:` — это **список именованных наборов условий**. Каждое новое
объявление проверяется по **всем** наборам сразу (не только по первому
подходящему), и в уведомлении будет указано, под какой набор (или наборы,
если подошло сразу под несколько) оно попало. У каждого набора **своя
категория сайта** — можно одновременно мониторить, например, "Электровелосипеды"
одним набором и "MTB велосипеды" другим:

```yaml
filters:
  - name: "Bosch Gen5, M/L, 700Wh+, до 1500км"
    site: {...}
    must_include: [...]
    criteria: {...}
    exclude_any: []

  - name: "Карбоновый Мтб до 1000е"
    site: {...}
    must_include: [...]
    criteria: {...}
    exclude_any: []
```

**Чтобы добавить новый набор** — скопируйте блок целиком (от `- name:` до
следующего `- name:` или до конца файла), вставьте копию под первым
набором и измените в ней название и условия. **Чтобы отключить набор** —
удалите его блок или закомментируйте каждую строку символом `#`.

Внутри каждого набора:

**`site`** — фильтры сайта (соответствуют левой панели на 2bike.rs), простыми
текстовыми полями, без URL:
```yaml
site:
  category_url: "https://2bike.rs/cikloberza/mali-oglasi/bicikli-6/mtb-bicikli-7"
  hide_sold: true          # скрыть проданные
  hide_no_price: false     # скрыть объявления без цены
  brands: []                # напр. ["Cube", "Trek"] - список брендов см. в scripts/scraper.py (BRAND_IDS)
  price_min: null           # напр. 500 - фильтр САЙТА по цене (см. предупреждение ниже)
  price_max: null
  price_currency: "EUR"
```
`category_url` задаёт саму категорию — самое частое, что тут меняют, когда
нужен новый набор под другой раздел сайта. `price_min`/`price_max` здесь —
это фильтр САЙТА (влияет на то, что вообще попадёт в выдачу); используйте
его, только если уверены, что объявления без указанной цены вам не нужны —
неизвестно, как сайт обрабатывает "BEZ CENE" при таком фильтре. Для цены
"мягкого" типа (показывать и то, что без цены) — используйте `criteria.price_eur_max`
ниже, а не `site.price_max`.

Фильтр брендов (`brands`) на сайте, судя по всему, относится к бренду
велосипеда, а не мотора — для поиска по мотору надёжнее текстовый поиск
в `must_include`. Город/радиус в фильтрах сайта пока не поддержан —
скажите, если понадобится, добавлю.

**`must_include`** — список групп `any_of`. Объявление должно содержать хотя
бы одно слово из **каждой** группы (группы между собой — И, слова внутри
группы — ИЛИ). Добавить новый обязательный критерий — добавить ещё одну
группу `any_of`. Добавить синоним к существующему — дописать строку в
нужный `any_of`. Пустой список `[]` — нет обязательных текстовых условий
(полезно, когда категория сайта уже достаточно сужает выборку, а остальное
проверяют мягкие критерии ниже).

**`exclude_any`** — стоп-слова: если встретится любое из них, объявление
пропускается под этим набором, даже если остальное совпало. Удобно
отсеивать "куплю/ищу", запчасти и т.п.

**`criteria`** — числовые/технические критерии:
```yaml
criteria:
  battery_wh_min: 700       # минимальная ёмкость батареи, Втч
  mileage_km_max: 1500      # максимальный пробег, км
  frame_sizes: ["M", "L"]   # допустимые размеры рамы
  frame_materials: ["carbon"]  # допустимые материалы рамы (carbon/aluminum/steel/titanium)
  price_eur_max: 1000       # максимальная цена, EUR (по цене САМОГО объявления)
```
Сайт не даёт под эти параметры отдельный фильтр (или даёт его слишком грубо,
как с ценой — см. выше), поэтому все они ищутся в тексте/данных объявления
через простые правила (например "800Wh" → батарея, "predjeno 300 km" →
пробег, при этом "25 km/h" не путается с пробегом). Это эвристика, не точный
разбор: **для каждого критерия объявление отклоняется, только если значение
явно указано и не подходит под условие.** Если продавец не написал ёмкость
батареи, размер рамы, материал или цену — объявление НЕ отклоняется, чтобы
не пропустить реально подходящий вариант из-за неполного текста. Отклоняется
только если явно указано что-то другое (например размер XL при `["M","L"]`,
или явно "aluminijum" при `["carbon"]`). Чтобы отключить критерий — `null`
(для чисел) или `[]` (для списков).

Сравнение идёт по заголовку и полному тексту страницы объявления,
без учёта регистра.

### 2. Уведомления

**Telegram** — нужны 2 секрета репозитория: **Settings → Secrets and
variables → Actions → New repository secret**

| Секрет | Значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен бота от @BotFather |
| `TELEGRAM_CHAT_ID` | Ваш chat_id (см. ниже, как получить) |

1. В Telegram: `@BotFather` → `/newbot` → получить token
2. Написать боту любое сообщение
3. Открыть `https://api.telegram.org/bot<TOKEN>/getUpdates`, найти `"chat":{"id":...}`

**Email** — отдельных секретов не нужно. Вместо SMTP-пароля скрипт
создаёт GitHub Issue в этом репозитории на каждое подходящее объявление,
с упоминанием `@<владелец репозитория>` в тексте — GitHub сам присылает
за это email на адрес, привязанный к вашему GitHub-аккаунту (обычная
системная функция уведомлений GitHub, работает "из коробки"). Всё, что
для этого нужно, у workflow уже есть автоматически (`GITHUB_TOKEN`,
права `issues: write` в `.github/workflows/monitor.yml`).

Убедитесь, что в настройках вашего GitHub-аккаунта включены email-уведомления
для упоминаний: **Settings → Notifications → убедитесь, что "Email" отмечен
для "Participating, @mentions and custom"**.

Письмо будет выглядеть как обычное уведомление GitHub про issue, а не
как отдельное красивое письмо — зато без единого пароля.

### 3. Запуск

Workflow срабатывает автоматически по расписанию. Проверить/запустить вручную:
**Actions → Monitor mali oglasi → Run workflow**.

### 4. Ручное сканирование "что сейчас есть" (без ожидания новых объявлений)

**Actions → Monitor mali oglasi → Run workflow**, отметить галочку
**scan_recent**, указать имя набора фильтров (`scan_filter_name`, по
умолчанию "Карбоновый Мтб до 1000е") и сколько страниц просмотреть
(`scan_max_pages`, по умолчанию 15 = до ~480 объявлений).

В отличие от обычной проверки, это не смотрит на `data/seen.json` и не
ищет только новое — проверяет широкий срез уже существующих объявлений в
категории набора и присылает результат ОДНИМ письмом/сообщением в виде
нумерованного списка ссылок, а не отдельным уведомлением на каждое
объявление. Полезно, чтобы сразу увидеть, что фильтр в принципе находит,
не дожидаясь появления новых объявлений.

Важная оговорка: сайт не показывает дату объявления в списке, поэтому
точной границы "за последний месяц" нет — вместо неё скрипт просматривает
заданное число страниц (новые/поднятые объявления сверху, как обычно).
Если 15 страниц окажется мало или много для примерно месяца — поменяйте
`scan_max_pages` при запуске.

## Ограничения GitHub Actions (бесплатный план)

- Публичные репозитории: неограниченные минуты для cron.
- Приватные репозитории: 2000 минут/месяц бесплатно.
- Scheduled workflows автоматически отключаются, если в репозитории не было
  push более 60 дней — в этом случае нужно вручную включить workflow заново
  (Actions → workflow → Enable).
- Точность cron не гарантирована день-в-день (может быть задержка в несколько минут).

## Как работает поиск по критериям

Каждый набор фильтров указывает `site.category_url` на отфильтрованную сайтом
подкатегорию (например "Električni bicikli" или "MTB bicikli") — это
надёжнее, чем скачивать всю категорию "Bicikli" (5944+ объявлений) целиком
и фильтровать вручную. Скрипт собирает объявления по всем таким URL из всех
наборов (одинаковые URL запрашиваются один раз) и объединяет результат — то
есть каждое объявление в итоге проверяется по ВСЕМ наборам фильтров, а не
только по тому, из чьей категории оно пришло.

Список объявлений на сайте не содержит текста описания — только заголовок,
цену и продавца. Поэтому для НОВЫХ объявлений (которых ещё нет в
`data/seen.json`) скрипт дополнительно открывает страницу самого объявления
и ищет ключевые слова/критерии в полном тексте страницы. Уже виденные
объявления повторно не проверяются.

Список отсортирован сайтом по дате публикации/**поднятия** (новые и
пролонгированные — сверху), поэтому скрипт подгружает страницы по 32
объявления одну за другой, пока не встретит объявление, которое уже видел
раньше (до 10 страниц за один запуск, для защиты от зависания при сбоях).

## Отсеивание поднятых/пролонгированных объявлений

Продавцы могут "поднимать" старые объявления — тогда они снова оказываются
на первой странице, хотя объявление не новое. Чтобы их не путать с
реально новыми:

- У каждого объявления есть числовой id (стабильный, не меняется при
  поднятии). Скрипт запоминает **максимальный увиденный id**
  (`max_known_id` в `data/seen.json`).
- Объявление считается по-настоящему новым, только если его id **больше**
  этого максимума. Старое поднятое объявление имеет id меньше максимума —
  оно будет пропущено, даже если раньше не встречалось скрипту.
- Первый запуск (когда `data/seen.json` ещё нет) только строит базовый
  список и запоминает текущий максимальный id — уведомления в этот раз
  не отправляются, чтобы не было лавины писем про уже существующие
  объявления.

## Статус

Парсер рабочий (проверен на реальной разметке сайта), уведомления в Telegram
и через GitHub Issues (email) протестированы и работают.

**Важно:** сайт 2bike.rs защищён Cloudflare, которая блокирует запросы с
облачных/дата-центровых IP (в том числе GitHub Actions) — даже через
headless-браузер (Playwright), см. раздел ниже. Поэтому сейчас мониторинг
запускается **локально**, с обычного домашнего компьютера — с домашнего IP
защита срабатывает значительно реже.

## Локальный запуск на своём компьютере (Windows)

### 1. Установка

1. Установите Python 3.11+ с [python.org](https://www.python.org/downloads/)
   (при установке отметьте галочку "Add python.exe to PATH").
2. Скачайте/клонируйте этот репозиторий на компьютер.
3. Откройте командную строку (cmd) в папке репозитория и выполните:
   ```
   pip install -r requirements.txt
   playwright install chromium
   ```

### 2. Секреты

Скопируйте [`.env.example`](.env.example) в файл `.env` (в той же папке,
рядом с `config.yaml`) и заполните значения — `.env` в `.gitignore`, наружу
не уйдёт:

- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` — как получить, см. раздел
  "Уведомления" выше.
- `GITHUB_TOKEN` — Personal Access Token с правом на issues в репозитории
  (создаётся на github.com: **Settings → Developer settings → Personal
  access tokens → Fine-grained tokens → Generate new token**, выбрать
  репозиторий `yazyninAK/Main`, права **Issues: Read and write**).
- `GITHUB_REPOSITORY=yazyninAK/Main`, `GITHUB_NOTIFY_USER=yazyninAK` —
  можно оставить как в примере.

### 3. Проверка вручную

```
python scripts\main.py
```
Первый запуск — это baseline (без уведомлений, ожидаемо). Если хотите сразу
проверить доставку уведомлений — `python scripts\test_notify.py`.

### 4. Планировщик заданий Windows (автозапуск 2 раза в день)

1. Win+R → `taskschd.msc` → Enter.
2. **Создать задачу** (не "простую задачу" — нужно больше настроек).
3. Вкладка **Общие**: имя, например "Мониторинг велосипедов". Отметить
   "Выполнять вне зависимости от того, выполнён ли вход пользователя".
4. Вкладка **Триггеры** → Создать → Ежедневно, время 09:00 → ОК. Повторить
   ещё раз для 21:00 (два отдельных триггера в одной задаче).
5. Вкладка **Действия** → Создать → Действие "Запуск программы":
   - Программа: полный путь к `run_monitor.bat` (например
     `C:\Users\ВыИмя\Main\run_monitor.bat`)
   - Рабочая папка (Start in): та же папка с репозиторием.
6. ОК, сохранить. Лог каждого запуска пишется в `monitor_log.txt` рядом
   с `.bat` файлом — полезно для проверки, что всё отработало.

### 5. Если Cloudflare всё равно блокирует

В `.env` попробуйте `SCRAPER_HEADLESS=false` — тогда при каждом запуске
будет ненадолго открываться настоящее окно браузера вместо фонового
режима, что выглядит более "по-человечески" для защиты сайта. Скрипт уже
пытается использовать ваш установленный Chrome (не тестовую сборку из
Playwright) — это тоже увеличивает шанс пройти проверку.
